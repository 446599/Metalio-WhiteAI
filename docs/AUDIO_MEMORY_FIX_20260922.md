# 扬声器无声：BLE 静态内存回归修复

基线：`57df42054fd78934f777a014f0c45bdd25440167`；上一版用户实测有声：`093e9df1811de0b0670879bffb61d9cd138df8c4`。
证据来源：用户提供 `WhiteAI-Audio-Memory-Handoff-20260922.zip`。

## 症状与判断

交接记录报告 UI、Wi-Fi 和会话正常，但 AI 回答及闹钟无声。附件的闹钟日志可独立确认播放任务连续创建失败，最大连续内部内存为 13824 字节；所需播放栈为 24576 字节。约 8 MiB PSRAM 空闲不能满足此内部栈申请。交接记录的静态段表报告共享内部静态占用从 146155 增至 166455 字节，其中 IRAM text 从 88727 增至 107351。符号之和与 ELF 段之和不同，不把两种统计混用。

原控制栏的 BLE 扫描通过 NimBLE 初始化函数把控制器代码和数据链接入固件；扫描结束释放任务和控制器动态资源，不能去掉镜像中常驻的 IRAM 代码。采用交接建议的“产品移除 BLE 发现”路线，优先恢复语音与铃声，不根据仅有铃声的栈水位盲目缩栈。

## 修改范围

1. 新增默认关闭的 `WHITEAI_EXPERIMENTAL_BLE_DISCOVERY` 编译选项。默认 CMake 不编入扫描实现、不由主组件依赖 `idf::bt`；旧 HAL 接口返回明确不支持，不加载控制器。实验选项保留原扫描源码，但开启后必须独立验证静态/动态内存预算，不能作为普通产品构建发布。
2. 控制栏取消默认 BLE 扫描按钮和热区，只保留蓝牙音频模式说明。Wi-Fi、媒体音量、铃声/震动、笔记、阅读、键盘与黑白字体逻辑不变。外置 UART/I2S 蓝牙音频模块与 ESP32 BLE 控制器不同，未更改外置模块、引脚或 AT 命令。
3. 保持采集 28672、播放 24576、自检 49152 字节的内部栈及原分配器，不移到 PSRAM。补充真实 PlaybackLoop 每条退出/continue 路径的低水位统计，包括 TTS 解码、重采样、I2S 成功及错误路径。
4. 构建新增 `audio-memory-budget`，检查最终 ELF 而非只检查 Flash 镜像容量。上限 IRAM 97280、共享内部静态 151552 字节；拒绝链接 NimBLE/控制器入口。`.dram0.dummy` 是已计入 IRAM 的地址别名填充，不重复累计。此门限是静态回归护栏，不保证运行时最大连续块。

没有修改 sdkconfig、分区、NVS 数据格式、字体文件、LUT、屏幕 DMA bounce 缓冲、USB 初始化或音频采集/播放协议。

## 诊断字段

`XIAOZHI_STATS?` 保留原有字段，并增加：

| 字段 | 含义 |
| --- | --- |
| `play_stack` | 播放任务观察到的最小剩余栈字节数 |
| `play_tts_stack` | 至少处理过一个 TTS 队列包时观察到的任务低水位 |
| `play_tts_n` | TTS 队列包路径采样次数；0 表示尚未测到 |
| `play_alloc_fail` | 播放任务创建失败计数 |
| `play_need` | 本构建播放栈字节数（24576） |
| `largest` | 当前 INTERNAL + 8BIT 最大连续空闲块 |

`play_tts_stack` 是 FreeRTOS 任务生命周期高水位的快照，包含先前更深的路径，不是独立的 Opus 栈占用。错误解码路径也采样，故不能只凭 `play_tts_n>0` 声称播音成功，应结合 `decoded`、错误计数和实际声音。0 剩余不会被后续较大值覆盖。

## 可复现验证

`python3 tools/check_audio_playback.py` 提取并执行生产 PlaybackLoop/任务创建逻辑，模拟 RTOS、编解码器和 I2S，覆盖分配失败后重试、11 种播放路径、并发最小值和有效 0 水位；同时运行 ELF 护栏单元测试。不是把模拟编解码作为真实 TTS。

`python3 tools/check_mono_controls.py` 验证默认无扫描实现；`WHITEAI_TEST_BLE=1 python3 tools/check_mono_controls.py` 仅验证实验 UI/调度 mock。原回归和真实字体预览继续执行。

完整 ESP-IDF 6.0.1 `idf.py build` 自动生成 `build/audio_memory.json` 并实施门限；缺工具、缺 ELF、段解析异常或超预算都失败，不降级成通过。最终运行记录和构建前后数值在提交交付时补记。

## 上机验收

关闭占用串口的浏览器/监视器。在原 ESP-IDF 6.0.1 环境重新 build，检查内存报告通过、设备分区和实际端口一致后仅执行 app-flash，不重写分区、OTA 选择、NVS 或字体。

先验证本地闹钟出声，再进行真实语音对话并检查 `decoded` 增加、`play_tts_n>0`、`play_alloc_fail` 不增长和实际扬声器声音。随后反复进入控制栏、Wi-Fi 页面、中文笔记/阅读，再复测铃声与 TTS。记录 `largest` 与栈水位。编译和主机测试不替代这些物理验收；本次未连接实体设备。

## CI 实际构建结果

验证运行：https://github.com/446599/Metalio-WhiteAI/actions/runs/35680222813

同环境对照：故障版本内部静态 166620 字节，修复版 146512 字节，减少 20108 字节；IRAM 总占用分别 108544 / 89856 字节。修复 ELF 未链接受检 BLE 入口，故障版被新增检查实际拒绝。

上述静态统计包含 vectors 和 text_end 对齐段，排除重复的 .dram0.dummy 别名；与交接文档的正文代码统计口径有小额差异。IRAM .text 从 107351 降至 88727 字节，与交接所列旧版有声代码大小一致，不等同于实测动态堆。

16 组主机检查通过，包括 11 个生产播放循环分支场景及 10 项 ELF 检查单测；默认控制/阅读检查 4406 次 CHECK，实验 BLE mock 4408 次，输入/联网 3176 次，记忆 504 次。硬件、RTOS、编解码/I2S 均按测试用途模拟。实际字体绘图和输入路由生成 5 组各 89 帧，共 445 帧（另有 5 张总览），通过缺字和越界检查。

完整 ESP-IDF 6.0.1 构建 1398 个步骤通过，应用 3142768 字节（0x2ff470），5 MiB 应用槽剩余约 40%；字体和分区表哈希保持不变。build/audio_memory.json 由构建实际校验生成。以上不是实体音频验收，未测修复后运行时最大连续块或实际 TTS 峰值。

验证运行中的 prepare/host/baseline/firmware 均成功；首次 publish 因 Actions token 无工作流写权限而失败。产品源文件由本次独立发布步骤按原产物哈希确认提交；常规工作流配置由仓库连接单独写入，没有修改已通过测试的产品代码，也没有关闭检查。
